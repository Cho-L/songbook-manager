# Phase 3.2 — 실시간 가사 싱크 · 노래방 UX

## 1. 기존 코드 조사 결과 (재작성하지 않은 것)
| 항목 | 조사 결과 |
|---|---|
| 재생 시간 | `useYouTubePlayer` 가 IFrame API `getCurrentTime()` 을 **재생 중에만 300ms 폴링**(그 외 상태 변화 때 1회). 시간 취득 가능 → 이를 기준으로 사용 |
| 재생 상태 | 훅이 상태를 밖으로 내보내지 않았다 (재생 불가 감지용으로만 사용) |
| 가사 파싱/줄 계산 | `parseLyrics` + `findCurrentLyricIndex(lines, t)` — 정상. 그대로 사용 (`{발음}` 보조 줄은 Phase 3.1 규칙대로 앞 줄에 붙어 인덱스 불변) |
| ConcertMode | SongMode 와 같은 훅/줄 계산 사용. 같은 방식으로 연결 |
| OBS 메시지 | 줄이 바뀔 때 + 5초 heartbeat 로 `lines/lineIndex/synced` 전송. **재생 상태·재생 시간은 보내지 않았다**(`playback` 필드는 있으나 미사용) |
| 싱크 보정 | 자동으로 찾은 가사(캐시)의 `warp`(±0.1~1.0초)만 존재. **DB에 저장된 싱크 가사에는 보정 수단이 없었다** |

## 2. 구현
- **플레이어 상태**: `useYouTubePlayer` 가 `phase`(playing/paused/buffering/ended/idle)·`seekCount`·`getNow()`·`getRate()` 를 추가로 제공. 재생 중 200ms, 그 외 1초 간격으로 시간을 읽어 **이벤트 없이 일어난 탐색도 ≤1초 안에 감지**. 탐색은 "정상 진행에서 1.5초(정지 중 0.75초) 이상 벗어남"으로 판정. YouTube 가 제공하는 `getCurrentTime/getPlaybackRate/onStateChange` 만 사용. 시간 정보를 못 읽으면(플레이어 없음) 기존처럼 수동/무싱크로 남고 임의 타이머로 싱크를 흉내 내지 않는다.
- **곡별 싱크 보정**: SongMode 에 `−0.5 / 현재값 / +0.5` (현재값 버튼=0초 초기화). 이 브라우저 localStorage 에 곡별 저장(범위 ±30초, 0.1초 단위) → **DB 변경 없음**. 자동 찾은 가사에는 기존 `싱크 보정(warp)` 이 이미 시간표에 반영돼 있어 이중 적용하지 않도록 새 버튼은 숨김. 공연(ConcertMode)은 같은 저장값을 읽어 쓴다(조절 버튼은 없음). **다른 기기·브라우저에는 보정값이 공유되지 않는다.**
- **노래방 표시**: 줄 역할을 `data-role=past|current|next|other` 로 구분(지난 줄 40% · 현재 강조+확대 · 바로 다음 줄 95% · 나머지 60%), 현재 줄 발음도 함께 강조, 밝은 배경에서는 진한 강조색, 긴 줄 `break-words` 줄바꿈. **줄 단위 LRC 만 지원 — 단어/음절 하이라이트는 구현하지 않았다**(해당 타임스탬프 데이터가 없음).
- **OBS 동기화**: SongMode/ConcertMode 가 `playback`(실제 플레이어 상태), `times`(줄별 시작 시각, 보정 반영), `pos`(발신 순간 재생 위치), `rate`, `off`, `seek` 를 기존 Supabase Realtime Broadcast + BroadcastChannel 로 전송. OBS 는 **받은 시각** 기준으로 `playing` 일 때만 위치를 진행시켜 줄 전환 시점을 스스로 계산(원문·발음은 같은 인덱스) — 발신/수신 시계를 비교하지 않는다. OBS 는 플레이어를 제어하지 않는다.
  - 전송 빈도: 상태 변화(재생/일시정지/버퍼링/탐색/줄 변경) 즉시 + 재생 중 **2초마다** 위치 보정(일시정지·미재생은 5초). 곡 하나 재생 중 대략 초당 0.5~1건.
  - 예상 지연: **네트워크 편도 지연만큼** OBS 가 뒤처진다(Realtime 보통 수십~수백 ms, 중계 400ms 시뮬레이션에서 올바른 줄 확인). 줄 전환은 OBS 쪽에서 자체 계산하므로 줄마다 메시지 지연이 누적되지 않고, 2초마다 재보정된다. 지연을 측정해 보정하지는 않는다.
  - 끊김/재연결: 메시지가 끊기면 마지막 위치에서 **최대 12초만** 진행하고 멈춘다(15초 후 오버레이는 기존대로 사라짐). 재연결 후 첫 메시지(또는 다음 2초 heartbeat)로 즉시 재동기화. 같은 발신자의 낮은 ts(지연 도착한 옛 이벤트)는 기존 로직대로 무시. 곡 변경 시 새 `lines/times` 로 통째로 교체되어 이전 곡 상태가 남지 않는다.
  - 호환: `times/pos` 가 없는 예전 발신자나 타임스탬프 없는 곡은 기존 `lineIndex` 방식 그대로.

## 3. DB / 스키마
**변경 없음** (SQL·롤백 없음). 라이브 메시지에 선택 필드(`times, pos, rate, off, seek`)만 추가 — 예전 오버레이는 무시한다.

## 4. 실제 환경에서 확인할 것 (샌드박스 미검증)
- 실제 YouTube IFrame 의 `onStateChange` 순서(특히 탐색 시 BUFFERING→PLAYING/PAUSED)와 광고/배속 환경에서의 시간 값 (테스트는 같은 API 를 흉내 낸 가짜 플레이어)
- 실제 Supabase Realtime 으로 다른 PC 의 OBS 에 전송했을 때의 지연·순서·재연결 동작 (테스트는 BroadcastChannel 중계로 시뮬레이션)
- OBS 브라우저 소스(CEF)에서의 타이머 정확도와 백그라운드 스로틀링

## 5. 남은 한계
- 줄 단위 싱크만 지원(단어/음절 하이라이트 없음). 보정은 곡 전체 오프셋(템포 차이는 못 맞춤).
- 보정값은 브라우저별 저장. 방송 PC 와 편집 PC 가 다르면 방송 PC 에서 맞춰야 한다.
- OBS 지연은 측정/보상하지 않는다(편도 네트워크 지연만큼 늦음).
- 영상 광고 구간 등 플레이어가 시간을 이상하게 돌려주는 경우 탐색으로 오인될 수 있다(방송 상태 즉시 재전송이 늘 뿐 오동작은 아님).

# Phase 3.1 — 가사 검색·적용·한글 발음

## 1. 조사로 확정한 원인 (코드 추적 + 목(mock) 재현)
| 증상 | 확정한 원인 |
|---|---|
| 한글 제목의 일본어 곡을 못 찾음 | (a) `useAutoLyrics` 가 곡의 제목/가수 별칭(직접 입력 + 기본 사전)을 검색에 전혀 쓰지 않았다. 기본 사전에 `아이묭 ↔ あいみょん ↔ Aimyon` 이 있어도 무시됨. (b) 점수 계산이 "한글 vs 일본어 제목"을 비교할 수 없어 0점. (c) MusicBrainz 별칭은 라틴 문자만 채택해 일본어 원제가 버려졌고 한글 가수명은 MB 에서 거의 매칭되지 않는다. 재현: `너는 록을 듣지 않아 / 아이묭` → 요청 3회 모두 한글만 보내고 `not-found`. |
| 후보는 뜨는데 가사가 안 보임/적용 안 됨 | (a) 후보 요약(`CandidateSummary`)에 본문이 없고, 후보를 고르면 **전체 검색을 다시** 돌려 후보를 재탐색했다(결과가 달라지면 "고른 후보를 다시 찾지 못했어요"). (b) 적용 결과가 **localStorage 캐시에만** 저장되고 곡 데이터(DB)는 바뀌지 않았다 → 다른 기기/캐시 삭제 시 사라짐. (c) 미리보기(전체 가사·타임스탬프)가 없었다. (d) 시간 태그가 깨진 syncedLyrics 도 "싱크 있음"으로 표시될 수 있었다. |
| 일본어/영어에 한글 발음 없음 | 발음 변환 코드와 데이터 구조가 없었다 (`phonetic.ts` 는 검색용 자음 골격 비교일 뿐). 가사 저장 필드는 `Song.lyrics` 문자열 하나. |

외부 API: LRCLIB(`/api/search`) — 검색 응답에 `plainLyrics`/`syncedLyrics` **본문이 이미 포함**된다(별도 본문 요청 불필요). MusicBrainz — 별칭 조회용.

## 2. 변경 요약
- 검색: 곡 별칭(직접 입력+기본 사전)을 검색 단계·점수에 사용, 원어(가나/한자)·영문·로마자 별칭 허용, 가수만 아는 경우 "가수의 곡 목록"을 후보로 제시(자동 선택 안 함), 가타카나↔히라가나 정규화, 곡당 총 요청 상한 14회·같은 검색어 중복 제거·LRCLIB 요청 공유/5분 캐시, 오류 분류(network/rate-limit/server/client/invalid) + 한국어 안내.
- 오선택 방지: 제목 별칭은 **가수가 맞을 때만** 인정, 문자 체계가 달라 비교 불가한 후보는 사용자가 미리보기로 확인 후 선택. 가사 없는 후보·깨진 LRC 는 "가사 있음/싱크 있음"으로 표시하지 않음.
- 후보 → 전체 미리보기(제목·가수·싱크 여부·줄 수·원곡/MR 길이 차이·줄별 타임스탬프) → 적용. 후보 선택 시 재검색 없음.
- 적용: **곡에 저장(DB)**. 기존 가사가 있으면 확인 단계 + 직전 가사 1회 백업(되돌리기). 저장 실패 시 기존 가사 유지. 싱크 없는 가사는 안내 + 곡 수정 화면(수동 [분:초] 편집) 링크. 기존 평문 가사가 있으면 "저장된 가사 유지 + 시간만 입히기" 선택 가능.
- 발음: 가사 텍스트에 `{발음} …` 보조 줄(아래 3절). 일본어 가나 → 한글 규칙 변환, 영어 → CMU 발음사전 기반 변환(필요할 때만 로드), 줄 상태 `자동 / 검토 필요 / 지원 불가`, 저장 전 미리보기·직접 수정, 자동 저장 없음.
- 표시: SongMode(원문만/원문+발음 토글), OBS 가사 오버레이(`lp=on|off`, Studio/설정 화면 토글), 같은 줄 인덱스로 함께 전환.

## 3. 데이터 구조 (DB 변경 없음)
`Song.lyrics` 텍스트 안에 보조 줄을 둔다:
```
[00:10.00] 君が好きです
{발음} 키미가 스키데스
{번역} 너를 좋아해요        ← 미래용(지금은 표시 안 함)
```
- `parseLyrics` 가 보조 줄을 앞 줄의 `pron`/`trans` 로 붙이고 별도 줄로 세지 않는다 → 줄 인덱스/타임스탬프/기존 로직 불변, 보조 줄이 없는 기존 데이터는 결과 동일.
- 기존 에디터·백업(JSON/CSV)·가져오기는 그대로 동작(보조 줄도 그냥 텍스트). 이 규칙을 모르는 옛 화면에서는 한 줄이 더 보일 뿐 데이터는 안 깨진다.
- 라이브(OBS) 상태 `pron?: string[]` 은 `lines` 와 같은 길이·같은 인덱스(없으면 필드 생략 → 예전 오버레이/발신자와 호환). 정밀 재생시간 동기화는 추가하지 않았다.
- **새 SQL 없음**(롤백 불필요). 새 npm 의존성: `cmu-pronouncing-dictionary`(ISC, 약 4.7MB — 영어 발음 생성 버튼을 누를 때만 별도 청크로 로드).

## 4. 발음 정확도 한계 (과장 금지)
- 일본어: 가나만 있는 줄은 규칙 변환(가장 신뢰). 흔한 한자 단어 약 60개만 읽기를 추정하고 해당 줄은 "검토 필요". 그 외 한자는 읽지 않고 원문 그대로 두며 "지원 불가". 조사 は/へ 는 '와/에' 여부를 알 수 없어 "검토 필요". 장음·촉음은 단순 규칙.
- 영어: 사전 기반이지만 한글 외래어 관례로 옮기는 근사치(받침/연음/노래의 늘임은 반영 안 됨). 사전에 없는 단어는 원문 유지 + "검토 필요".
- 한자 읽기 전체를 지원하려면 형태소 사전(kuromoji, ~40MB) 또는 AI API 가 필요하다 — **승인 없이 추가하지 않았다**.

## 5. 외부 서비스·저작권
LRCLIB 는 공개 커뮤니티 DB(API 키 없음). 가사는 사용자가 적용한 곡의 `lyrics` 로 **그 노래책 소유자가 직접 저장**할 때만 DB 에 들어가며, 앱이 자동으로 수집·재배포하지 않는다(자동 결과는 이 브라우저 캐시). 서비스 약관/가사 저작권 판단은 운영자 책임이며 이 문서는 법률 검토가 아니다. 스크래핑·인증 우회 없음.

## 6. 운영 환경 미검증
실제 LRCLIB/MusicBrainz 응답 형태(우리는 목으로 검증), 실제 Supabase 저장·RLS, Realtime 로 `pron` 전송, 실제 OBS 브라우저 소스 렌더링은 샌드박스에서 확인하지 못했다.

## 7. 배포
SQL 없음. 일반 빌드/배포(`npm run build`)만 하면 된다. 이번 작업에서는 운영 DB·Cloudflare·GitHub 에 아무것도 하지 않았다.
